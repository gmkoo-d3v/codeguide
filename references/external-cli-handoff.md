# External CLI File Handoff Contract

Extracted from SKILL.md for Phase 1 coverage audit; updated in Phase 6 to keep command-template policy runner-neutral. This is the external-CLI-specific instance of the general delegation-handoff rule in `references/orchestration-contract.md` (durable Markdown handoff file first, short instruction plus absolute path second) — the mechanics below (output-capture path, sanitization, provenance) are the additional constraints that apply when the delegate runs as a separate process rather than an in-session sub-agent.

## External CLI File Handoff Contract
- External LLM reviews are runner-neutral. `config/ai_model_registry.json` declares runners, route-qualified model ids, aliases, quota groups, default reviewers, quota-error patterns, and quota-stop policy.
- Write the full request into a Markdown handoff file first instead of passing the full prompt as a shell argument.
- Structure request handoff files as metadata plus `Why`, `What`, `How`, `Where`, `Verify`, then payload.
- Pass only a short instruction and the absolute handoff file path to CLIs that can reliably read the handoff file in the approved runner context. For runners whose safe non-interactive mode disables file tools or cannot read workspace paths, the wrapper may stream the already-written handoff file content on stdin while keeping the Markdown request file as the durable source of record.
- The invoking wrapper must name an explicit absolute command-output path through stdout redirection or an equivalent runner-supported output option; a path mentioned only inside the prompt is not enough.
- The wrapper may sanitize that raw command output into the durable Markdown response file and delete the raw capture; treat ambiguous model claims such as "saved to the plan file" as invalid unless the claimed path equals the command-level output or sanitized response path.
- Runner command templates live in the registry-backed runner implementation; this policy records handoff invariants and must not pin CLI flags or model ids.
- External reviewer model selection is runner-specific: wrappers must not mutate runner settings; use the runner's globally selected model when no documented per-call flag exists, and use a registry-owned per-call model flag only when the installed CLI exposes one and the route records the requested CLI model. agy CLI 1.1.12+ supports `--model`, so registered non-preconfigured agy routes receive `--model <cli_model>`.
- OpenAI/Codex routes must run in STANDARD processing mode only: never pass fast/priority service-tier flags or config overrides (and never register routes that imply them) — priority processing multiplies token cost (~1.5x) for latency this workflow does not need (user directive 2026-07-10).
- In approved runner environments, direct external CLI invocation is the primary path. In Codex app sessions, the permission remediation is to request explicit user approval for the external CLI command and rerun it through the user-approved unsandboxed execution path; do not automate Terminal UI, do not mutate runner settings, and do not treat manual paste as the primary automation path.
- When the operating agent is Codex or ChatGPT, invoke Anthropic (`claude`) CLI routes non-sandboxed (user-approved escalated execution) from the FIRST attempt, not only as post-failure remediation: the claude CLI needs Anthropic API network access and OS credential-store access, both blocked by Codex sandboxes, so a sandboxed first attempt burns the review round on a predictable auth failure. Both executors fail fast with this remediation when `CODEX_SANDBOX` or `CODEX_SANDBOX_NETWORK_DISABLED` carries a truthy value; explicit falsy values (`0`, `false`, `off`, `no`, `none`, empty) are ignored, so a stale inherited marker can be neutralized by unsetting it or setting it falsy. Absence of both markers cannot prove the shell is unsandboxed — ChatGPT-driven operation must follow this rule by contract, not by detection.
- If the platform blocks private workspace egress even after explicit user approval, classify it as `platform_permission_blocked` and move execution to the approved external-review runner rather than trying UI or terminal workarounds.
- If the user approved the exact external CLI step but the runtime still routes the escalation through an automatic guardian reviewer and blocks private workspace egress, classify it as `platform_permission_blocked`: do not keep retrying, do not drive Terminal UI as an indirect workaround, and ask the user to switch the thread/workspace permission mode so escalation prompts go to the user approval path.
- If a runner reports authentication failure inside a Codex/app sandbox, including `Not logged in`, `Please run /login`, `Failed to authenticate`, `Invalid authentication credentials`, or `API Error: 401`, treat it first as a sandbox/keychain permission boundary, not proof that the user's account is logged out. Rerun the same command through the user-approved unsandboxed execution path before asking the user to operate a terminal manually; if it still fails there, classify it as `auth_blocked` and ask the user to log in.
- When a Shadow v2 close gate is tracking that condition, record the blocked route with the runner route and reason, for example `--blocked-review external_cli:agy=platform_permission_blocked`, so downstream reports preserve the permission-mode remediation.
- Use the manual handoff route only as a last-resort fallback when the platform permission mode cannot be changed and the user explicitly accepts user-operated CLI execution: run `run_external_plan_reviews.sh` with `--manual-handoff-only`, show the generated `*.manual-command.md` files to the user, have the user run those commands directly in their own terminal, then rerun the wrapper with `--ingest-manual-responses` to redact, parse, write reports, and generate provenance.
- For ad-hoc implementation-review packets that contain diffs or source excerpts, prefer an inline-only packet that does not ask the external CLI to inspect filesystem paths. If filesystem inspection is intentionally required, attach the project root with the configured runner workspace mechanism.
- External CLI review must use `risk_preflight_status: approved` with concrete `approval_ref`, exact `approved_next_step`, and main-thread `risk_preflight_recorded_by`; `pass` is not enough because the call crosses an external-service boundary.
- Capture CLI output into a redacted Markdown response file before parsing or normalizing it into `docs/report/`; request parser-compatible bullet fields when downstream automation depends on fixed response fields, but preserve malformed sanitized output for retry diagnostics.
- After parsing an external CLI response successfully, write a wrapper-generated `*.provenance.md` manifest beside the response file with evaluator runner, requested/actual route, requested/actual CLI model, evaluator_model_selection, quota_fallback_triggered, verdict, request file, response file, response hash, command-response path, `raw_capture_deleted: true`, and `sanitized_response: true`.
- Keep durable handoff artifacts under project docs, preferably `docs/orchestration/<task-id>/external-cli/<plan-version>/<round>/`, so long prompts and raw responses survive shell argument limits and are easy to inspect.
- Treat local external-review provenance as consistency evidence, not tamper-proof attestation. In a writable workspace, a human can forge matching response/request/provenance files; if tamper resistance is required, stop for an external signing or audit mechanism instead of accepting local files.
- Do not put raw secrets in handoff or response files; redact sensitive values before writing durable Markdown artifacts.
- **Quota exhaustion**: `run_external_plan_reviews.sh` and `external_review_runner.py` load aliases, runner routes, quota groups, default reviewers, and quota-error patterns from `config/ai_model_registry.json` or `CODEGUIDE_MODEL_REGISTRY`. When a registered route exhausts quota, stop and ask the user to switch the runner's globally selected model, then rerun with a reviewer route that records that selection. Do not auto-edit runner settings.
