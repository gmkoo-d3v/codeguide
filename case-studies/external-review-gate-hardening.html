4. 여전히 LLM 지침 준수에 의존하는 영역

  • 사용자가 정말 승인했는지. 로컬 증거는 일관성 증거일 뿐 위변조 방지 증명이 아닙니다. 쓰기 권한이 있으면 해시까지 맞춘 가짜 증거 세트나 chosen_by: user 결정 파일을 만들 수 있습니다.
  • 게이트를 실제로 거치는지. run_codeguide.sh를 쓰지 않고 직접 수정하거나 --task-status planned로 구현하면 우회됩니다. CI·pre-commit 연결은 추가하지 않았습니다.
  • 요구 사항의 기록. external_review_required_for, required_review_routes, 상태 필드는 에이전트가 직접 적습니다. 비워 두거나 약한 route만 적어도 게이트는 알 수 없고, wrapper가 이 필드를 자동 기록하지도 않습니다.
  • 리뷰 이후의 변화. 계획서가 리뷰 뒤에 바뀌었는지, request 내용이 변조됐는지는 확인하지 못합니다(wrapper가 계획서·request 해시를 기록하지 않음). 이 부분은 사용자 트랙이라 wrapper는 건드리지 않았습니다.
  • 범위의 경계. 닫힌(done) 작업은 의도적으로 재검사하지 않습니다. 실제 코퍼스의 유일한 implementation_start 작업은 기록된 리뷰가 revise이고 provenance도 없지만 이 예외로 걸리지 않습니다. waiver는 계획 버전에 묶이지 않고, 외부 CLI route가 아닌 native 서브에이전트 리뷰는 이 게이트로 증명할 수 없습니다.

5. 확인이 필요한 변경

  • 손으로 쓴 provenance는 더 이상 인정되지 않습니다. 수동 리뷰는 wrapper의 --ingest-manual-responses로 다시 넣어야 합니다.
  • 리뷰 필수 작업에서 기본 옵션(--task-status in_progress)으로 run_codeguide.sh를 돌리면 게이트가 막습니다. 계획만 갱신할 때는 --task-status planned를 쓰세요.
  • strict에서 in_progress이면서 리뷰가 필요한 작업이 게이트 미충족이면 이제 실패합니다.
