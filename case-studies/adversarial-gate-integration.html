3. 해결된 계약 충돌

verdictobjection / counterproposal / rebuttalresidual_risk구현 승인
accept키 존재 필수, 값은 비어도 됨값 필수증거 세트가 완전할 때만
revise키 존재, 값 필수값 필수불가 (형식은 유효)
blocked키 존재, 값 필수값 필수불가 (형식은 유효)
  • 충돌: wrapper는 빈 반박 필드의 정상 accept를 첫 시도에서 받아들였는데, 제 검증기는 세 필드에 값을 요구해 같은 응답을 승인 게이트에서 거부했습니다. TC-01이 실제로 이 모순을 재현했습니다(`response is missing required review field objection` 등).
  • 수정: 키 부재(None)와 빈 값("")을 구분해 계약대로 적용했습니다. 네 키는 모든 verdict에서 있어야 하고, residual_risk는 항상 비어 있으면 안 되며, 반박 3필드는 accept가 아니면 값이 있어야 합니다. 검증을 우회하거나 기대값을 느슨하게 바꾸지 않았고, 검증기는 여전히 accept만 승인합니다.
  • 변이 확인: 수정 전 검증기를 되돌리면 TC-01과 PARITY-01이 실패하고, 수정 전 wrapper 파서를 되돌려도 실패합니다. 테스트가 어느 쪽 이탈도 잡습니다.
  • Shadow v2 게이트: 필드 규칙은 같아서 코드를 바꾸지 않았습니다. 다만 키 문법이 다릅니다. wrapper와 검증기는 열 0의 - key: 줄만 읽고, Shadow v2는 다른 글머리표·들여쓰기·대소문자도 받아들입니다. 손으로 쓴 응답은 Shadow v2만 통과할 수 있고, 진짜 wrapper 산출물은 셋 모두 통과합니다. 계약 문서에 기록했습니다.
  • 공유 계약 검토: 두 파이썬 읽기 주체는 코드를 공유할 수 있지만 bash wrapper는 그럴 수 없고, 다른 브랜치의 게이트와 테스트까지 건드려야 해서 범위를 넓히지 않았습니다. 대신 규칙을 한 곳의 실행 가능한 표(PARITY-01)로 두고 wrapper와 검증기가 모두 통과해야 하게 했습니다. 코드 통합은 후속 과제입니다.

6. 실제 외부 CLI 호출 0회설치된 agy·claude·codex가 실제로 있어서 차단이 필요했습니다

  • 실제 바이너리는 ~/.local/bin/agy, ~/.local/bin/claude, /opt/homebrew/bin/codex에 있습니다. 테스트 PATH에서 이 디렉터리를 뺐고, 모든 CLI 이름(agy, claude, codex, gemini, antigravity)에 호출을 기록하고 거부하는 트립와이어를 달았으며, CODEGUIDE_*_BIN은 mock을 가리킵니다. 매 테스트의 teardown이 트립와이어 로그가 비었는지 확인합니다(GUARD-01/02).
  • 기존 스위트도 같은 방식의 PATH로 돌렸습니다. 트립와이어 로그는 한 줄, agy models뿐입니다. 위 external_review.bats:1799 테스트가 command -v agy로 agy를 찾아 agy models를 실행한 것이고, 트립와이어가 가로채 종료 코드 97을 돌려 실제 바이너리는 실행되지 않았습니다.
  • 주의: 이 테스트는 차단 없이 돌리면 실제 agy models를 실행합니다. 기존 baseline 실행에서도 그랬을 수 있습니다. 적용하지 않았지만, agy가 있어도 mock 목록을 쓰거나 명시적 허용 환경 변수가 있을 때만 실행하도록 바꾸는 것을 권합니다(agy 트랙 파일이라 요청 없이는 수정하지 않았습니다).

8. 남은 구조적 우회와 무결성 문제해결했다고 보고하지 않습니다

현재 계약상 통과하는 테스트(TC)와 향후 강화가 필요한 항목(KL)은 분리했습니다. KL 테스트는 약점의 현재 동작을 그대로 고정한 것이라 강화되면 일부러 깨집니다.

  • KL-1 리뷰 뒤에 계획서가 바뀌어도 감지하지 못합니다(계획서 해시 없음).
  • KL-2 리뷰 뒤에 Request 원문이 바뀌어도 감지하지 못합니다(request 해시 없음).
  • KL-3 하네스를 거치지 않는 직접 수정이나 --task-status planned 실행은 게이트를 거치지 않습니다.
  • KL-4 리뷰 요구 필드(external_review_required_for)를 에이전트가 비워 두면 리뷰가 필요 없는 작업처럼 보입니다.
  • KL-5 완료된 작업의 승인 이력은 다시 검사하지 않습니다.
  • waiver의 결정 문서는 형식만 확인하며 사용자의 실제 승인은 암호학적으로 증명하지 못합니다.
  • Shadow v2 게이트의 키 문법이 다른 두 읽기 주체보다 느슨합니다.
  • 20-rules-shadow.sh의 SIGPIPE 경쟁이 부하에서 strict 검증을 흔듭니다(기존 결함, 이번에 손대지 않음).

9. main 병합 가능 여부

조건부 가능. 계약 통합 관점에서 병합을 막는 요인은 없습니다: 충돌 없는 병합, 불일치 1건 해결, 신규 24/24 세 번 통과, 기존 675개에서 새 실패 0건, 실제 CLI 실행 0회. 사용자의 승인만 남았습니다.
  • 스킬 저장소: main(13a1597)이 통합 브랜치의 조상이라 fast-forward로 병합됩니다. 이 병합은 adversarial 브랜치(643a1d7)도 함께 main에 들입니다.
  • docs 저장소: main 체크아웃의 미커밋 변경이 정리된 뒤 병합합니다.
  • 병합해도 기존 실패 3건(기존 2건, 실제 agy를 부르는 테스트 1건)과 위 8개 한계는 그대로입니다.
